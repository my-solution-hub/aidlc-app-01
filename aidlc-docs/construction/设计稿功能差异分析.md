# .pen 设计稿功能 vs 后端 MVP — 差异分析

> **分析日期**: 2026-06-11  
> **分析依据**: 产品意图 (original-intent.md)、需求文档 (requirements.md)、API 接口规范 (api-docs/)、用户故事 (stories.md)

---

## 结论先行

**这 7 项功能均不在 MVP 需求范围内**。设计稿 (.pen) 是产品远期愿景，MVP 需求明确界定了最小可行范围。以下逐项分析其与 MVP 的关系、后端当前状态及建议优先级。

---

## 逐项分析

### 1. 用户部门字段 + 用户统计 `users/stats`

| 维度 | 分析 |
|------|------|
| **MVP 需求中** | ❌ 不在范围。需求仅定义两种角色（员工/管理员），未提及部门概念 |
| **API 规范中** | ❌ `UserDTO` 无 department 字段；无 `/api/admin/users/stats` 端点 |
| **后端现状** | UserEntity 有 employeeId 字段，无 department 字段，无统计端点 |
| **缺失类型** | **P2（体验优化）** — 不阻塞核心流程，属后期组织管理增强 |
| **实现难度** | 低（加字段 + 聚合查询） |
| **建议** | MVP 后期迭代，优先级低于核心链路完善 |

---

### 2. 员工确认收货 `confirm-receipt`

| 维度 | 分析 |
|------|------|
| **MVP 需求中** | ❌ 明确排除。`FR-ORDER-005`: "采用**线下自取**模式，系统仅记录兑换信息"；Scope Out: "物流配送跟踪" |
| **API 规范中** | ❌ 订单状态流转为 `PENDING_DELIVERY → DELIVERING → COMPLETED`，由管理员操作，无员工确认收货端点 |
| **后端现状** | `PUT /api/admin/orders/{id}/status` 仅管理员可更新状态 |
| **缺失类型** | **P2（体验优化）** — MVP 用线下自取替代物流确认 |
| **实现难度** | 中（需新增员工端状态变更端点 + 状态机扩展） |
| **建议** | 产品从自取转为快递模式时再实现，属商业模式变更 |

---

### 3. 收货地址簿 + 下单带地址

| 维度 | 分析 |
|------|------|
| **MVP 需求中** | ❌ 明确排除。`FR-ORDER-005`: "线下自取模式"；Scope Out: "物流配送跟踪" |
| **API 规范中** | ❌ `ExchangeRequest` 无地址字段 |
| **后端现状** | 无 Address 实体、无地址簿端点、无配送模型 |
| **缺失类型** | **P2（远期功能）** — 与物流系统集成绑定，MVP 明确排除 |
| **实现难度** | 高（新增 Address 领域、地址簿 CRUD、下单关联、配送集成） |
| **建议** | 作为 V2 需求评估，需同时引入物流/快递服务集成 |

---

### 4. 兑换记录 DTO 扩展字段（运费/兑换后余额/状态时间线等）

| 维度 | 分析 |
|------|------|
| **MVP 需求中** | 部分相关。`FR-ORDER-007`: "兑换记录包含产品信息、消耗积分、兑换时间、兑换状态"，未要求运费/余额/时间线 |
| **API 规范中** | `ExchangeRecordDTO` 包含基础字段，无运费(deliveryFee)/兑换后余额(balanceAfter)/状态时间线(statusTimeline) |
| **后端现状** | DTO 仅含核心字段；状态流转已有 `trackingNumber`，无历史记录表 |
| **缺失类型** | **P2（体验增强）** |
| **各子项分析** | |
| — 运费 | P2-远期（与物流绑定，MVP 无物流） |
| — 兑换后余额 | **P1-有价值** — 前端可自行计算，但后端返回更可靠 |
| — 状态时间线 | P2（需新增 order_status_history 表） |
| **建议** | 兑换后余额可在 DTO 中快速增加（低成本）；运费和时间线作为 V2 |

---

### 5. 积分规则扩展字段（适用范围/发放方式/图标）

| 维度 | 分析 |
|------|------|
| **MVP 需求中** | 部分相关。`FR-ADMIN-004`: "配置积分自动发放规则（额度、周期）"，未要求适用范围/图标 |
| **API 规范中** | `PointRuleDTO` 有 name/ruleType/pointValue/triggerCondition/status，无 scope/distributionMethod/icon 字段 |
| **后端现状** | PointRuleEntity 有 `triggerCondition`(JSON) 可扩展存储；无 icon 字段 |
| **缺失类型** | **P2（管理增强）** |
| **各子项分析** | |
| — 适用范围(scope) | P2（可存入 triggerCondition JSON 中，无需新字段） |
| — 发放方式 | P2（已有 ruleType 区分 FIXED/EVENT/PERFORMANCE） |
| — 图标(icon) | P2-最低优先级（纯 UI 展示，加一个 varchar 字段即可） |
| **建议** | scope 可通过现有 triggerCondition 扩展；icon 加字段即可，成本极低 |

---

### 6. 员工订单 keyword 搜索

| 维度 | 分析 |
|------|------|
| **MVP 需求中** | 未明确要求。`FR-ORDER-006`: "员工可以查看自己的兑换历史记录"，未提搜索 |
| **API 规范中** | `ListMyExchangeRequest` 仅有 page/size/userId/status，**无 keyword 字段** |
| **后端现状** | 管理端 `ListExchangeRecordRequest` 有 keyword，**员工端无** |
| **缺失类型** | **P1（用户体验）** — 兑换多了后无搜索体验差 |
| **实现难度** | 极低（在 `ListMyExchangeRequest` 加 keyword 字段 + Mapper 加 LIKE 条件） |
| **建议** | 可立即实现，工作量 < 30 分钟 |

---

### 7. 商品多图 `images[]`

| 维度 | 分析 |
|------|------|
| **MVP 需求中** | 部分相关。`FR-PROD-002`: "产品图片" — 未明确单图/多图 |
| **API 规范中** | `ProductDTO` 使用 `imageUrl`（单个 string），非 `images[]` 数组 |
| **后端现状** | ProductEntity 有 `imageUrl` 单字段；FileController 支持上传单文件返回 URL |
| **缺失类型** | **P2（体验增强）** — MVP 单图足够，多图是展示优化 |
| **实现难度** | 中（需要：新增 product_images 关联表 或 JSON 数组字段 + 前端轮播组件） |
| **建议** | MVP 单图满足基本需求；V2 迭代时支持多图上传+排序 |

## 建议给前端团队的回复

> 这 7 项来自设计稿远期规划，**不在 MVP 后端范围内**。MVP 需求明确界定:
> - 线下自取（无地址/物流/确认收货）
> - 单图展示
> - 基础 DTO 字段
>
> **可快速响应的（P1，建议本迭代做）：**
> - #6 员工订单 keyword 搜索 — 工作量极小
> - #4 兑换后余额字段 — DTO 加一个字段
>
> **可低成本顺手做的：**
> - #5 积分规则 icon 字段 — 加一个 varchar
>
> **需要产品决策的（P2，建议 V2）：**
> - #1 部门字段 — 需定义组织结构模型
> - #2/#3 确认收货/地址 — 需商业模式从自取改为配送
> - #7 多图 — 需新增关联表/前端轮播
> - #4 状态时间线 — 需新增历史表
