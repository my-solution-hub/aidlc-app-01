# AWSomeShop 五模块功能缺口分析报告

> **分析时间**: 2026-06-10
> **分析方法**: 基于 AI-DLC 逆向工程，对比 original-intent（产品意图）、requirements.md（需求规格）与实际代码实现
> **分析范围**: API Gateway、Auth Service、Product Service、Points Service、Order Service

## 二、按模块逐项分析缺失功能

### 🌐 API Gateway — 缺失功能

| # | 缺失功能 | 需求来源 | 优先级 | 说明 |
|---|---------|---------|--------|------|
| GW-1 | **限流/熔断** | NFR-PERF-001 (1000+用户) | 高 | 无 Rate Limiting 和 Circuit Breaker，高并发下无保护 |
| GW-2 | **请求参数校验** | NFR-SEC-004 (防攻击) | 中 | 网关层缺少统一的请求体大小限制、SQL注入/XSS 过滤 |
| GW-3 | **API 版本管理路由** | 最佳实践 | 低 | 当前硬编码 /api/v1，无版本协商机制 |
| GW-4 | **健康检查端点** | 运维最佳实践 | 中 | 缺少 /health 和 /ready 端点，不利于容器编排健康检测 |
| GW-5 | **请求链路追踪** | 可观测性 | 低 | 无 traceId/spanId 注入，分布式排障困难 |

### 🔑 Auth Service — 缺失功能

| # | 缺失功能 | 需求来源 | 优先级 | 说明 |
|---|---------|---------|--------|------|
| AUTH-1 | **用户注册端点** | FR-AUTH-001, 产品意图 | 🔴 高 | 无注册功能，用户只能靠数据库直接插入 |
| AUTH-2 | **注册时调用 Points 初始化积分** | 跨服务依赖 | 🔴 高 | 新用户注册后无积分账户，Points 功能不可用 |
| AUTH-3 | **密码修改/重置** | 最佳实践 | 中 | 用户无法自助修改密码 |
| AUTH-4 | **用户启用/禁用管理** | 管理需求 | 中 | UserEntity 有 status 字段，但无管理端点 |
| AUTH-5 | **登出黑名单接入校验链路** | 安全闭环 | 中 | logout 写入 Redis 黑名单，但 validate 未检查黑名单 |
| AUTH-6 | **Token 刷新机制** | 用户体验 | 低 | JWT 24h 过期后只能重新登录，无 refresh token |
| AUTH-7 | **登录日志/审计** | NFR-SEC-003 | 低 | 有 failedLoginAttempts 但无独立审计日志表 |
| AUTH-8 | **管理员创建/管理用户** | FR-ADMIN (隐含) | 中 | 管理员无法在系统内创建新员工账号 |

### 📦 Product Service — 缺失功能

| # | 缺失功能 | 需求来源 | 优先级 | 说明 |
|---|---------|---------|--------|------|
| PROD-1 | **产品搜索（按名称/分类）** | FR-PROD-006 | 🔴 高 | 需求明确要求搜索，当前仅有列表分页 |
| PROD-2 | **产品删除（逻辑删除）** | FR-PROD-001 | 中 | 有 status 变更但无明确的删除/下架流程 |
| PROD-3 | **商品图片上传** | FR-PROD-002, 需求文档 | 中 | 当前仅存 URL 字符串，无文件上传能力 |
| PROD-4 | **库存不足自动下架** | 业务完整性 | 中 | 库存为 0 时标记 SOLD_OUT，但无自动通知管理员 |
| PROD-5 | **产品批量导入** | 运营效率 (200+产品) | 低 | FR-PROD-004 要求 200+ 产品，逐个录入效率极低 |
| PROD-6 | **分类 CRUD 完整端点** | FR-ADMIN-003 | 中 | 有 list，缺 create/update/delete 分类的管理端点 |
| PROD-7 | **产品排序/推荐** | 用户体验 | 低 | 无热门/新品/推荐排序逻辑 |

### ⭐ Points Service — 缺失功能

| # | 缺失功能 | 需求来源 | 优先级 | 说明 |
|---|---------|---------|--------|------|
| PTS-1 | **积分定期自动发放（定时任务）** | FR-POINT-001 | 🔴 高 | 需求明确要求"系统自动按固定额度定期发放"，完全未实现 |
| PTS-2 | **管理员查看所有员工积分余额** | FR-ADMIN-001 | 🔴 高 | 管理员无法纵览全部员工的积分状态 |
| PTS-3 | **积分发放规则配置（额度、周期）** | FR-ADMIN-004 | 高 | 有 PointRule 管理，但缺少与定时任务的联动执行 |
| PTS-4 | **管理员手动批量发放积分** | 运营效率 | 中 | 当前 adjust 是单用户操作，无批量发放入口 |
| PTS-5 | **积分变动操作人记录** | FR-POINT-005 | 中 | 流水记录缺少"操作人"字段（谁发放/扣除的） |
| PTS-6 | **积分余额防超扣校验** | 业务完整性 | 高 | 扣减时需要原子校验 balance >= amount，防并发超扣 |
| PTS-7 | **积分统计报表** | 运营分析 | 低 | 无全局积分发放/使用的汇总统计 |

### 🧾 Order Service — 缺失功能

| # | 缺失功能 | 需求来源 | 优先级 | 说明 |
|---|---------|---------|--------|------|
| ORD-1 | **兑换前余额校验** | FR-ORDER-002 | 🔴 高 | 需在下单前明确校验积分是否充足，给出友好提示 |
| ORD-2 | **兑换前库存校验** | FR-ORDER-003 | 🔴 高 | 需在下单前明确校验库存，避免先扣积分后发现无货 |
| ORD-3 | **兑换取消/退货退积分** | 业务完整性 | 中 | 员工误兑换后无法取消，积分无法退回 |
| ORD-4 | **Saga 超时处理** | 分布式可靠性 | 高 | 若 Points/Product 服务超时，Saga 状态悬挂无清理机制 |
| ORD-5 | **幂等性保障** | 分布式可靠性 | 高 | 重复提交可能导致重复扣积分/库存 |
| ORD-6 | **兑换频率限制** | 防刷保护 | 中 | 无限制单用户短时间内重复兑换同一商品 |
| ORD-7 | **管理员发货/确认收货状态流转** | 业务闭环 | 中 | 有 trackingNumber 字段但无完整状态机 |
| ORD-8 | **兑换通知（站内信/邮件）** | 用户体验 | 低 | 兑换成功后无通知机制 |

## 三、跨模块/系统级缺失

| # | 缺失功能 | 影响范围 | 优先级 | 说明 |
|---|---------|---------|--------|------|
| SYS-1 | **统一异常处理与错误码体系** | 全部服务 | 高 | 各服务无统一的 BusinessException + ErrorCode 规范 |
| SYS-2 | **API 文档（Swagger/OpenAPI）** | NFR-MAINT-002 | 高 | 需求明确要求，当前完全缺失 |

| SYS-7 | **配置外部化** | 运维最佳实践 | 低 | 数据库连接等配置硬编码在 application.yml |

## 四、优先级排序 — 建议实施路线

### 🔴 P0（阻塞核心流程，必须立即修复）

1. **AUTH-1**: 用户注册端点
2. **AUTH-2**: 注册时初始化积分
3. **PTS-1**: 积分定期自动发放
4. **PTS-2**: 管理员查看所有员工积分
5. **PROD-1**: 产品搜索
6. **ORD-1/ORD-2**: 兑换前余额+库存预校验

### 🟠 P1（影响系统可靠性和完整性）

7. **ORD-4/ORD-5**: Saga 超时 + 幂等性
8. **PTS-6**: 积分防超扣
9. **AUTH-5**: 登出黑名单接入校验
10. **SYS-1**: 统一异常处理
11. **SYS-2**: API 文档
12. **SYS-8**: 服务间容错
13. **GW-1**: 限流/熔断

### 🟡 P2（提升用户体验和运营效率）

14. **AUTH-4/AUTH-8**: 用户管理完善
15. **PROD-6**: 分类 CRUD
16. **PTS-3**: 发放规则与定时任务联动
17. **ORD-3**: 兑换取消/退积分
18. **ORD-7**: 发货状态流转
19. **GW-4**: 健康检查
20. **SYS-3/SYS-4**: 种子数据 + Docker Compose

## 五、总结

基于对 AWSomeShop 5 个后端模块的全面分析：

- **已实现**: 核心 CRUD 和基础业务流程（登录、产品管理、积分规则、兑换记录、Saga 编排）
- **最大缺口**: 
  - 用户注册链路断裂（无注册 → 无法自助加入系统）
  - 积分自动发放未实现（核心商业模式所依赖的"积分来源"不存在）
  - 搜索功能缺失（200+ 产品规模下，无搜索 = 不可用）
  - 分布式事务可靠性不足（幂等、超时、防超扣）
- **建议**: 按 P0 → P1 → P2 顺序推进，先通核心链路，再补全可靠性，最后优化体验
